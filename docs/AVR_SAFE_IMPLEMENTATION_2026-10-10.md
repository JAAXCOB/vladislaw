Дата: 10 октября 2026. Основание: `AVR_AI_AUDIT_2026-10-10.md`, исходники main `cf4667bec55494320032740c3fca937e1905c3a8`, отдельного Excel-бота `beaa88360a1e58764d60b4de006c1e5dac03a9ed`.

## Состояние и границы результата

Все изменения подготовлены **локально**. Production, действующие базы, ключи и подписки MAX не менялись. Новые ветки, push, запуск deploy/recovery workflow, платные API и покупки серверов не выполнялись. Доступ к текущим серверным файлам и журналам отсутствует: совпадение GitHub с production и восстановимость настоящей резервной копии пока не подтверждены.

Main содержит частичные PHP-патчи сайта, а не полный релиз. Рабочий Excel-бот найден в существующей ветке `claude/max-excel-evacuation-automation-zxuvb4`. Нельзя выкладывать содержимое main поверх document root сайта или заменять серверный config.php без сверки. Отсутствуют полные `webpush.php`, `partner_orders_helpers.php`, `api/partner_order_action.php`, `api/partner_order_sync.php` и другие зависимости.

Локальный PHP-кандидат закрывает найденные обходы проверки оплаты; он не заменяет транзакционный адаптер. До его готовности ИИ запрещены изменения финансов и распределение водителей. Пилотная SQL-схема предназначена для стенда, не для непосредственного импорта рабочих данных.

Отдельно нужны разрешённые сетевые направления SSH/SFTP; текущее HTTP-подключение к GitHub не означает доступ к серверам. Если SSH недоступен на тарифе, достаточно выгрузки оператором без предоставления полномочий на запись.

## 3. Резервные копии и восстановление

Не создавать новую резервную копию на production в рамках этого этапа. Получить существующую проверяемую копию или snapshot от владельца; если её нет, подготовить окно создания с оператором после согласования процедуры. Один архив текущих активно изменяемых JSON/XLSX не гарантирует согласованность.

Состав копии сайта: полный код с закрытыми зависимостями, data/orders/workers/users/ledger/finance/payouts/payments/B2B/settings, uploads, web-server/PHP/cron config и отдельно зашифрованные секреты. Excel: оба XLSX, schema, open jobs, sync queue, ack queue, inbox, payroll state, unit/Caddy, dependency pins. Включить все реальные пути после инвентаризации. SQL — штатный consistent dump/snapshot с проверкой движка; JSON/XLSX — единый snapshot файловой системы либо короткая остановка **всех** писателей в будущем окне. Копии должны относиться к одной точке восстановления и иметь время/версию/манифест.

Шифрование: age/GPG/провайдерное хранилище с ограниченным доступом; ключ вне архива. Отдельный доверенный манифест SHA256 и целостность внешнего зашифрованного архива. Хэши, лежащие внутри того же изменённого архива, не доказывают подлинность. Не хранить реальные копии в репозитории, Pages или CI artifacts публичного проекта.

Проверка стенда:

1. Создать отдельный хост/контейнер/локальный каталог. Запретить исходящие MAX/банк/SMTP/production API, cron, reminders, deploy hooks. Сначала обезличить телефоны, адреса, токены, пользователей; для тестов использовать mock credentials и отдельные test chat/account. Не запускать восстановленные production units автоматически.
2. Проверить архив и внешний манифест. Для ZIP до 256 MiB инструмент проверяет полный перечень, размер и SHA256 всех файлов; отклоняет traversal, symlinks, лишние/повторные/повреждённые элементы и существующий target:

   ```bash
   python -m scripts.verify_restore --archive /workspace/stage/backup-fixture.zip --manifest /workspace/stage/trusted-manifest.json --target /workspace/stage/restore-drill-001
   ```

   Манифест: `{"version":1,"files":{"data/orders.php":{"bytes":N,"sha256":"..."}}}`. Для больших/SQL/зашифрованных копий нужен отдельный штатный механизм после расшифрования внутри стенда. ZIP-инструмент проверяет байты и безопасное извлечение, не финансовую согласованность.
3. Проверить парсинг PHP-prefixed JSON, уникальность ID, ссылки orders↔workers↔ledger↔finance↔payouts, статусы/суммы, остатки, количество заявок и движение денег на точку snapshot. Сравнить итоговые обороты и доступные балансы с контрольным отчётом оператора, не пересчитывать и не исправлять историю автоматически.
4. Проверить оба XLSX: открытие openpyxl, листы/таблицы/формулы/стили/число строк/месяцы, сохранение тестовой копии, защита от formula injection. Проверить восстановленные очереди: pending/dead/sent, порядок replay, дубли и возможность retry без повторного назначения/начисления.
5. После обезличивания запустить приложение с mock bank/MAX/mail. Проверить роли, вход диспетчера/водителя, claim/отмена/завершение, B2B-разделение, платёж и выплату. Записать реальное время восстановления и потерю данных. Начальные цели для обсуждения: RPO ≤1 час для заявок/финансов, RTO ≤2 часа; текущие гарантии не установлены.
6. Хранение с малыми затратами: 7 ежедневных + 4 недельных копии, snapshot перед каждым релизом, внешняя зашифрованная копия; объём и расписание уточнить по серверу. Базы/копии при rollback не удалять.

Исторические ошибочные начисления исправлять согласованными компенсирующими проводками, не удалением строк. Полная модель refund/partial refund и payout остаётся отдельной обязательной работой.

## 5. Устранение встроенных секретов и ротация

В текущем config.php присутствуют встроенный dispatcher key и парольные SHA256. Значения не включать в отчёт или patch вне защищённого рабочего хранилища. Не считать их безопасными только потому, что production не менялся; подготовить замену каждого после проверки зависимостей.

1. Перечень **имён**, а не значений: MAX_BOT_TOKEN, MAX_WEBHOOK_SECRET, AV_RESCUE_API_KEY, dispatcher key/legacy password hashes, bank/SMTP credentials, AI credentials, CI server access. Проверить код, ZIP, историю Git, workflow, экспорт и логи локальным сканером с redacted output. Никаких значений в issue/Pages/PR. При разборе реального секрета использовать только secret references.
2. Выделить service credentials каждому компоненту: webhook, site partner endpoint, mailbox, deployment. Для Linux отдельный `EnvironmentFile` вне checkout 0600 и ограниченный service user; для PHP — env/FPM pool или файл вне document root с доступом только PHP-пользователю. Общий хостинг без env требует согласованного абсолютного include из закрытого пути. Секретный файл не должен попадать в web/download handler/backups без шифрования.
3. На стенде заменить только три встроенных define на загрузку проверенного bootstrap. `deployment/templates/secrets_bootstrap.php` — подготовленный вариант для env: никаких fallback, минимальная длина dispatcher key 32, формат hashes 64 hex. Проверить вход существующими ролями с **тестовыми** секретами, отсутствие публичной выдачи config, исключения и журнал. Дальше мигрировать legacy SHA256 на password_hash/password_verify при успешном входе с планом восстановления admin-доступа. Не менять пароль пользователя молча.
4. Для production заранее документировать владелец/consumer/provider, канал доставки новой версии, окно, health check, rollback и момент отзыва старого. Проверить новую конфигурацию стенда до генерации действующих ключей. Новые значения создаёт владелец в менеджере секретов; CI/чат их не печатает.
5. Partner key: если endpoint поддерживает key ID/две версии, краткое окно old+new, обновить клиент, подтвердить HMAC/авторизацию, затем отозвать old. Если не поддерживает — согласованное короткое окно с долговечной очередью. MAX webhook secret: staged receiver с версионированным endpoint/двойной проверкой только непустых разрешённых ключей, затем официальное обновление subscription и проверка доставки; поддержку нескольких подписок проверить до использования. Не менять текущую subscription на этом этапе.
6. Bot token: провайдер может отзывать старый сразу. Подготовить короткое окно, остановку outgoing worker в будущем релизе, очередь и безопасное возобновление без массового replay; обновить всех consumers, проверить /me и доступ только к разрешённому test chat. Bank key/SMTP/app password — аналогично, отдельно, без оплаты/отправок на стенде.
7. После успешной production-проверки отозвать old, проверить что старый отклоняется, убрать литералы из поддерживаемого кода/ZIP и предотвратить повторное добавление. Переписывание истории публичного репозитория — отдельная согласованная операция: оно не заменяет отзыв уже опубликованного секрета. Rollback после отзыва использует новый secret binding, а не воскресший старый ключ.

## 6. Транзакции и защита от одновременных изменений

Сервер сайта остаётся источником истины для заявок, назначений, пользователей и финансов; Excel — отчётная проекция. Не переносить полномочия в XLSX. Выбор DB после выяснения тарифа: если уже доступна MySQL/InnoDB — использовать её; для одного локального сайта без отдельной БД допустим SQLite с PDO_SQLite, локальным диском, WAL, foreign_keys и busy_timeout. Не размещать SQLite на NFS и не использовать одну SQLite между серверами. Не покупать DB-сервер до оценки существующих возможностей.

Контракт одной операции:

- Авторизовать actor и scope, валидировать команду, order version и стабильный idempotency key.
- В SQLite `BEGIN IMMEDIATE`; в InnoDB транзакция и `SELECT ... FOR UPDATE` на заказ/водителя/платёж. Единый порядок блокировок, ограниченный retry на deadlock/busy.
- Claim: `UPDATE ... WHERE version=expected AND status=new AND worker_id IS NULL`; rowcount=1, увеличить version, зарезервировать водителя. Уникальный active assignment не допускает два активных заказа одному водителю, если такой бизнес-режим подтверждён.
- Finance: подтверждение оплаты отдельной серверной записью, деньги integer minor units; проверить завершение, worker, B2B, соответствие captured amount/currency, расчёт ставок. ledger/finance summary/order flags/audit/outbox в **одной** транзакции. UNIQUE на provider payment ID, operation key, credit/debit scope. Одинаковый повтор возвращает прежний результат; другой payload с тем же ключом → 409.
- COMMIT до внешней отправки. MAX/mail/Excel выполняют outbox workers с backoff/dead-letter. Они не держат DB-lock во время сетевого запроса. Приход из Excel не переписывает авторитетные деньги/статус без проверенной команды сайта.
- Возвраты и выплаты: immutable reversal/payout operations с отдельными unique keys и сверкой; существующие строки не удалять. Payment captured → refund должен создавать компенсирующую проводку, не просто менять status.

Пилотная схема проверяет часть инвариантов, а не весь этот контракт. В частности, нужны полноценные migration/import/reconcile, отдельная модель finance/payout/reversals, неизменяемость проводок, enforcement ролей, API-адаптер и compatibility tests Android/админки. Trigger на INSERT не защищает произвольный UPDATE уже проведённой строки: закрыть такие операции правами DB/адаптера и проверками до production.

Миграция: восстановленная копия → строгий import, сохранение исходных IDs/цен/дат → сравнение количества/оборотов/балансов → dry-run на полном обезличенном snapshot → staging-нагрузка claim/settle/payment callback с дубликатами → краткое будущее окно блокировки всех writers, финальный импорт, переключение флага. Старые JSON оставить read-only архивом. Не вводить неконтролируемую двойную запись JSON+DB: она снова создаёт рассогласование. После новых записей в DB откат приложения возможен только на совместимую с DB версию; нельзя переключаться обратно на устаревший JSON и потерять заявки.

## 7. ИИ-управляющий и почта: минимальная установка

**На REG.RU:** сайт, auth/roles, API с версиями/idempotency, транзакционная DB, payment verification, audit/outbox, read-only панель контроля. Не запускать тяжёлые модели и почтовый crawler в PHP-запросе. **На Excel-сервере:** существующий webhook/Excel/payroll, независимые очереди, минимальные адаптеры MAX/mail и controller-service при наличии ресурсов. При недостатке RAM/диска — отдельный недорогой VPS, без покупки на этом этапе.

Минимум для controller без локальной LLM: Linux LTS, 1 vCPU, 1 GiB RAM, ~10 GiB свободного диска после OS и **дополнительно** измеренный запас под queues/logs/backups. Практический запас 2 vCPU/2 GiB RAM/20 GiB. Не запускать локальную LLM на таком минимуме. Сначала измерить нагрузку Excel/pandas/openpyxl и исключить OOM при одновременной работе. Бесплатный pilot использует существующий сервер, правила и mock/local deterministic router.

Контроллер: supervisor → policy gate → model router → отдельные узкие агенты заявки/водители/финансы/mail/ads/security → queue/outbox. Агенты не получают SSH/sudo, DB-write или полный .env. Разрешения через типизированные command APIs с audit, timeout, лимитами, allowlist и idempotency. Первый режим read-only, затем рекомендации человеку, только затем ограниченные обратимые операции. Финансы, публикация рекламы, ротация, обновление сервера — ручное подтверждение конкретного результата. Письма/заявки/чат — недоверенный контент: инструкции из них не изменяют полномочия агента.

Выбор модели: сначала правила/кэш/локальный extractor; сложность, необходимость tool use, приватность и оставшийся лимит определяют следующий backend. При отключённом backend — ручная очередь. Стартовые настройки `paid_api_enabled=false`, `daily_budget_minor=0`, `monthly_budget_minor=0`; вызов запрещён **до** HTTP-запроса. В будущем при отдельном разрешении резервировать верхнюю стоимость запроса атомарно, учитывать retries/таймауты/параллельные задачи, освобождать остаток по usage; лимиты по проекту/агенту/дню/месяцу. Цены версионировать, число токенов/timeout ограничить. Ошибка учёта бюджета → запрет вызова, не fallback на более дорогую модель.

Закрытый MAX control chat: allowlist chat **и user IDs**, ролевая проверка на каждую команду, команды с сроком/nonce, запрет полномочий по display name. Отчёты — короткие статусы без телефонов/ключей. Админка показывает задачи, budget, outbox/dead-letter, ошибки, restore evidence, pending approvals; защищена session/CSRF/MFA где доступно. Интерфейсные доработки сверить с `AVR_ADMIN_FUNCTIONAL_SPEC.md`.

**Яндекс:** выделенный технический ящик, IMAP TLS993 для чтения; SMTP TLS465/STARTTLS587 только после отдельного этапа отправки. На обычной почте использовать пароль приложения через secret store при разрешённом IMAP; OAuth выбирать после проверки типа Яндекс360/доступных протоколов и политики владельца. Не обещать универсальный OAuth для произвольного ящика. Ящики сотрудников не подключать целиком.

**Gmail:** OAuth authorization владельца, выделенный mailbox, первоначально `gmail.readonly`; refresh token в secret store. Не использовать gmail.modify/mail.google.com, если нужна только выборка. Для будущих черновиков/отправки добавить только необходимые scopes с отдельным согласием. Gmail API может не требовать оплаты за стандартное использование, но это не отменяет quotas/consent/verification; не подключать Cloud billing или платные модели.

В обоих случаях: message ID/IMAP UID+UIDVALIDITY для дедупликации, watermark/retry, запрет обработки вложений с макросами/исполняемых файлов, лимиты размера, сохранение только нужных полей, HTML sanitization, закрытое хранение/retention. На pilot не менять labels/read flags, не удалять/пересылать письма и не отправлять ответы; parser считает письмо входящими данными, не командой исполнения. Ответ — проверяемый draft в панели. Для IMAP проверить, что клиент использует BODY.PEEK и не выставляет Seen.

## 8. Безопасный порядок установки и отката

1. **Сейчас:** локальный кандидат + документация/тесты, без publication. Настроить защищённые read-only подключения и получить серверные исходники/снимки.
2. **Сверка:** собрать diff manifests и восстановить полный рабочий состав, особенно partner helpers и bank/payment writers; сохранить конкретный baseline обоих серверов. Выяснить frontend/mobile CSRF и API contracts.
3. **Стенд:** восстановление, обезличивание, блокировка исходящего production-трафика, воспроизводимые PHP/Python зависимости, DB-пилот. Проверить точную PHP-версию/расширения хостинга и bank fixtures.
4. **Кандидат релиза:** внедрить внешние secrets на стенде, MAX fail-closed, финансовый guard с legacy-payment reconciliation, транзакционный adapter. Проверить тестами и совместимостью. Без adapter финансовые writers/ИИ не включать.
5. **Защита CI до push в ветку бота:** manual dispatch/production environment с required reviewers, убрать незащищённый push-deploy, разделить build/test и install, read-only recovery. Существующий deploy-bot workflow и recovery scripts меняют рабочий сервер; не считать их безопасным способом аудита. При отсутствии GitHub environment approvals на тарифе оставить только ручную установку оператором и не хранить live deploy credentials в автоматически запускаемом workflow.
6. **Проверяемый release artifact:** утверждённый список файлов/хэши/миграции/секретные references, unit configuration, preflight, health, rollback, staging evidence. Не включать .env/data/XLSX в artifact, не использовать rsync --delete по site/checkout. Новая версия в отдельном каталоге releases; data и секреты вне release. Не выполнять произвольные postinstall из входящей заявки.
7. **Будущий production-релиз только после проверки и отдельного согласования:** snapshot, короткое окно миграции writers, atomic release switch где тариф поддерживает; для общего хостинга — проверенный последовательный план оператора с резервной копией и учётом mixed-version окна. Обновлять компоненты по одному с совместимым API-контрактом, не все сразу. Ротацию выполнять отдельно по проверенному плану.
8. **Контроль:** health, forbidden webhook tests, роль/claim, bank сверка, balances, MAX очереди, Excel формулы, mail read-only, audit privacy и backup status. Не отправлять тестовые сообщения в B2B production без отдельного разрешения.
9. **Откат:** code release switch на совместимую версию, сохранить очереди/новые данные/новые keys; остановить опасный новый writer, не откатывать банк и XLSX вслепую. Если схема менялась, использовать заранее проверенную совместимость или восстанавливать snapshot с учётом всех последующих событий, без потери оплат. Автоматически удалять/обнулять ledger или queues запрещено.
10. **ИИ pilot:** только наблюдение/рекомендации с нулевым API-бюджетом; затем почта read-only и панель; ограниченные действия после согласованных acceptance checks. Рекламу и финансовые полномочия вводить последними.

## 9. Результаты проверок

На локальных синтетических fixtures, без обращения к MAX, банку, почте или production:

- Main: **51 Python-тест прошёл** (включая 12 inventory/restore и 6 transactional-schema проверок).
- Excel-бот: **63 Python-теста прошли**, включая новую проверку пустого runtime-секрета и некорректного UTF-8 заголовка.
- PHP 8.4.24 CLI: **25 финансовых проверок прошли** — unverified paid запрещён, amount/currency/order/status mismatch запрещены, valid payment разрешён, repeat без дубля, conflict запрещён, cash и B2B сохраняют режим, ошибки записи и безопасный retry, незавершённый заказ не начисляет.
- PHP syntax: изменённые 5 файлов + secret template + harness — 7 файлов, без syntax errors.
- SQLite: два одновременных claim дают одного победителя; credit при неверной/возвращённой оплате запрещён, duplicate credit запрещён, ошибка outbox откатывает транзакцию.
- Restore: синтетический roundtrip, сохранение существующего target, corruption, traversal, symlink, oversize и неманифестированные файлы отклонены.

PHP получен из Debian-пакета в отдельный `/workspace/avr-php-runtime`, SHA256 пакета и зависимости сверены с HTTPS Packages metadata. Системные пакеты/серверы не устанавливались. Эта версия не подтверждает совместимость с пока неизвестным PHP на REG.RU. Неблокирующие Python deprecation warnings требуют будущего планового обновления зависимостей.

**Пока не проверено:** текущее production-состояние, настоящий restore/boot/RPO/RTO, реальные ответы эквайринга, полные partner APIs, миграция рабочих данных, нагрузка/ресурсы, Gmail/Yandex authorization, CI review gates. Это условия перехода к установке, не обещание уже работающего внедрения.
