## Правила проекта которые необходимо сохранить

Основание — действующий `AVR_WORK_PLAN.md`, а не предположения ИИ:

- Основной домен av-rescue.ru; существующие роли, единый аккаунт, Android и PWA сохраняются.
- Собственный парк: 35% обычного заказа. Сторонний исполнитель: 90%, комиссия 10%; оклейка и пороги 30/100/200 заказов уменьшают комиссию, минимум 7%, выплата максимум 93%.
- Положительная проводка driver_credit имеет холд по настройке, по умолчанию 48 часов.
- B2B и особенно B2B MAX не смешиваются с обычными финансами. Сейчас код исключает из них и `b2b_id`, и `source=max_partner`. Будущая архитектура сохраняет отдельные контуры `avr`, `b2b`, `max_partner`.
- Заявки MAX доступны своему парку, диспетчерам и администраторам; сторонним исполнителям доступ закрыт.
- Для партнёров сохраняются две Excel-таблицы, месячная вкладка, первая свободная строка и сумма в колонке сотрудника.
- Для карты MAX используется точка А; точка Б и название сервиса — в карточке. Название до скобок и адрес внутри скобок разбираются отдельно.
- Изменение тарифов, цены дополнительных работ и финансовых правил требует отдельного решения. ИИ не меняет действующие ставки самостоятельно.

## Распределение между серверами

| Сервер сайта | Сервер Excel-бота |
|---|---|
| PHP-сайт, существующая админка, клиентские и мобильные API | MAX ingestion для партнёрского и управляющего ботов, каждый с отдельной конфигурацией |
| Единственный авторитетный источник обычных заказов, аккаунтов, ролей, водителей, тарифов, банковских статусов, выплат | Главный управляющий, durable очередь задач, маршрутизатор моделей, учёт бюджета |
| Детерминированный подбор и резервирование водителя; переходы статусов; финансовый сервис | Специализированные агенты заявок, почты, аналитики финансов, рекламы, эксплуатации и безопасности |
| Минимальный шлюз интеграции: чистые read API и ограниченные command API; inbox/outbox сайта | Извлечение данных MAX, дедупликация и версии сообщений; отдельный реестр max_partner |
| Панель ИИ в админке, RBAC, подтверждения, аварийное отключение команд | Два Excel-экспорта, почтовые адаптеры, отчёты и наблюдение за очередями |
| Коды подтверждения Яндекс SMTP остаются в текущем пути | Чтение рабочих ящиков и подготовка ответов отделены от кодов подтверждения |

Это проектное распределение. Сначала нужно измерить свободную память, CPU и диск Excel-сервера. Если ресурсов недостаточно, начать с одного последовательного worker без дополнительного VPS; перенос на новый сервер — только по измерениям. Не уменьшать Yandex Cloud VM и не отключать диск/адрес по предположению о нагрузке.

Связь — HTTPS с сервисными ключами ограниченных прав; при доступной частной сети — через неё. Ключи отдельно для чтения, партнёрских команд и административного управления. Не использовать общий опубликованный dispatcher key. Запрос содержит schema_version, event_id/command_id, source, entity_id, entity_version, timestamp и trace_id. Подпись включает метод, путь и тело; timestamp и nonce защищают от replay. Команда повторяется с тем же idempotency key, максимум ограниченное число попыток с backoff, затем карантин.

MAX хранит исходный идентификатор `(bot_id, chat_id, mid)` и версии сообщения. Напоминание не создаёт новую заявку; изменение обновляет существующую версию. Если API не даёт отдельного event_id, формировать устойчивый ключ события из типа, идентификатора сообщения и нормализованной версии/хеша. Порядок событий проверяется; поздняя старая версия не затирает новую. Неоднозначное закрытие отправляется диспетчеру. Удаление сообщения не означает автоматически выполненную работу или удаление финансовых записей.

Excel — представление партнёрского реестра, а не второй источник истины. Один writer на книгу; экспорт с event/version checkpoint, временный файл и атомарная замена, сохранение формул и форматов. Частичный успех двух экспортов отражается отдельно, повторяется только незавершённый экспорт. Исправления в Excel требуют согласованного импорта с журналом, иначе следующий экспорт их перезапишет. Windows-папка владельца — место выгрузки, не обязательная зависимость серверного процесса.

## Главный ИИ управляющий

Управляющий — программный оркестратор с ограниченными инструментами. Цикл: принять событие → классифицировать по правилам → проверить права и бюджет → выбрать обработчик/модель → получить структурированный результат → проверить схему и бизнес-инварианты → сформировать предложение или разрешённую команду → записать итог и стоимость.

| Агент | Задача | Граница полномочий |
|---|---|---|
| Заявки | Разбор MAX/почты, адреса, техника, связи между сообщениями | Создаёт черновик; подтверждённые события max_partner — через ограниченный API |
| Диспетчер | Объяснение выбора, выявление зависших предложений | Предлагает кандидата; фактическое назначение выполняет общий серверный алгоритм |
| Финансы | Сверка банка, заказов, проводок и Excel | Только чтение и предложение исправления; ставки, выплаты и возвраты не исполняет самостоятельно |
| Почта | Классификация, сроки, черновики ответов | Не отправляет письмо до разрешённого сценария/подтверждения |
| Реклама | UTM, обращения, стоимость подтверждённого заказа, тексты и предложения | Не запускает кампании и не увеличивает расходы без подтверждения |
| Сайт | Черновики страниц, проверка ссылок и ошибок | Публикация и изменение кода проходят проверку и процедуру обновления |
| Безопасность и эксплуатация | Аномалии, резервные копии, отчёты об ошибках | Не получает unrestricted shell, банковские ключи или право удаления резервных копий |

Приоритет задач: приём событий и сохранность данных → действующие заявки → срочная почта → сверка → реклама. Агенты — логические обработчики одного сервиса, а не семь постоянно работающих LLM-процессов. Для каждой задачи хранить состояние, версию промпта/политики, результат, лимиты и причину решения. Не сохранять скрытые рассуждения модели; достаточно краткого объяснения и ссылок на факты.

## Выбор моделей и ограничение расходов

1. Правила, шаблоны, регулярные выражения, арифметика, дедупликация и кеш выполняются без LLM. Одинаковая версия сообщения повторно API не оплачивает.
2. Малый класс модели используется для свободного текста и JSON-извлечения; средний — для сложной почты/сводок; сильный — только для неоднозначной задачи с обоснованием. Рекламу и массовые сводки откладывать при дефиците бюджета.
3. Реестр моделей хранит provider, model_id, поддерживаемые форматы/инструменты, цены input/output, максимальный контекст, измеренное качество, задержку и разрешённые типы данных. Выбор программный по этим условиям; названия и актуальные тарифы задаются после проверки доступности API.
4. На старте один провайдер и максимум два разрешённых класса моделей. Неудачная проверка схемы допускает одну повторную попытку или одну эскалацию: максимум два платных вызова на задачу. Уверенность модели сама по себе не разрешает финансовую операцию.
5. Перед отправкой атомарно резервировать верхнюю стоимость входных токенов и max_output_tokens. Считать сумму потраченного и резервов всех параллельных задач; после ответа учитывать реальный usage. При таймауте с неизвестной стоимостью резерв не освобождать до сверки. Повторы учитываются как отдельные платные вызовы.
6. Лимиты: общий месячный, суточный, по агенту, задаче, модели, токенам и параллельности. Учитывать прочие платные инструменты отдельно. Предупреждения на 80% и 95%; при 100% — остановка новых платных вызовов, очередь для человека. Provider quota — дополнительный барьер, не единственный.
7. API-бюджет при установке — 0, LLM выключен. Предлагаемый пилот после решения владельца: $20 в месяц и $1 в сутки, с резервом 10% внутри общего лимита для срочных задач. Это потолок, не прогноз платежа. Рекламный бюджет задаётся отдельно и по умолчанию также 0.

Формула прогнозирования: `C = input_tokens / 1 000 000 × P_in + output_tokens / 1 000 000 × P_out`. Например, 20 разборов в день по 1500 входных и 300 выходных токенов за 30 дней дают 0,9 млн input и 0,18 млн output; цена равна `0,9 × P_in + 0,18 × P_out` плюс повторные вызовы. Это сценарий нагрузки, не установленный объём бизнеса. Кешировать по версии текста, модели, схемы и промпта; срок кеша учитывать вместе с политикой хранения персональных данных.

Локальную модель не устанавливать без измерения ресурсов и сравнения стоимости. Её содержание может стоить дороже небольшого API-бюджета. При недоступности модели сохранять событие, использовать шаблонный разбор и передавать неоднозначности человеку.

## Яндекс Почта Gmail и управление

Яндекс: входящая почта через IMAP TLS с отдельным паролем приложения либо поддерживаемой авторизацией выбранного типа ящика; отправка через отдельный SMTP credential. Gmail: OAuth 2.0, первоначально read-only, расширение на отправку только для утверждённого сценария. Проверить требования Google к OAuth-приложению и типу аккаунта до обещания готового подключения. Refresh tokens шифруются и остаются вне промптов, кода и логов.

Почтовый worker хранит mailbox_id, Message-ID/provider ID, IMAP UIDVALIDITY+UID или Gmail history checkpoint; повторный sync идемпотентен. Читает нужные папки и минимальный текст, вложения получает выборочно, проверяет тип/размер/вредоносный контент. Не пересылает в LLM OTP, банковские пароли и полные документы. Ответ — черновик с адресатом, темой, текстом и ссылкой на исходное письмо. Неоднозначный получатель и письма о деньгах требуют проверки. На старте нет удаления писем, автооткрытия ссылок и автозапуска вложений.

Закрытый MAX-чат: отдельный управляющий бот и разрешённый chat_id; user_id сопоставляется с действующим сотрудником сайта. Название чата и display name не являются авторизацией. При снятии роли доступ отзывается. Разрешённые команды: статус, незакрытые заявки, очередь, расходы, черновики, подтверждение конкретного действия, пауза ИИ. `message_callback` и права бота проверяются на тестовом чате до подключения.

Опасное действие показывается карточкой с объектом, суммой, ожидаемым эффектом и command_id. Подтверждение привязано к правомочному user_id, хешу предложения и версии объекта, действует ограниченное время; при изменении данных нужно новое предложение. Для выплат, возвратов, изменения ролей/тарифов, публикации и обновления серверов на начальных этапах требуется подтверждение в админке с повторной аутентификацией. Сообщение в чате не превращается в shell-команду.

Админка: новый раздел «ИИ управление» без замены существующей панели. В нём режим наблюдения/предложений/ограниченной автоматики, очередь подтверждений, история действий, расходы и резервы, состояние интеграций, версии настроек, последние резервные копии и кнопка остановки команд. Полные финансовые и почтовые данные видны только соответствующим ролям. Аварийная пауза блокирует выполнение, но оставляет durable приём событий.

## Защита журналирование и резервные копии

- Разделить доверенные инструкции и входящие сообщения. MAX, почта, вложения и сайты — недоверенные данные; просьба «выдай ключи» внутри письма не меняет права агента. Tool arguments проверяются независимо от LLM; allowlist методов, адресов интеграций и допустимых переходов.
- Каждый инструмент получает минимальные права. ИИ не имеет прямого доступа к файлам реестров сайта, секретам банка и конфигурации деплоя. MFA/повторная аутентификация для привилегированных действий, отдельная учётная запись worker, ограничения CPU/RAM, безопасные TLS и права на файлы.
- Перенести чувствительные данные за webroot; не полагаться только на префикс PHP exit. Исключить доступ к .env, backup ZIP и данным через веб-сервер. Ротация ключей и отзыв токенов проходят с проверкой потребителей.
- Журнал решения: trace_id, источник и версия, actor, агент, инструмент, объект, краткая причина, policy/model version, approval, результат, latency, usage/cost. Текст клиента, телефон, адрес, платёжные реквизиты маскировать; сырой архив при необходимости шифровать отдельно с коротким сроком хранения.
- Наблюдать возраст очереди, ошибки sync, потерю heartbeat, диск, свежесть GPS, расхождения банка/реестров, ошибки авторизации, расход API и дату последней успешной копии. /health проверяет процесс; отдельный readiness — хранилище/очередь. Уведомления не зависят от платного LLM.
- Предлагаемые цели пилота: RPO 1 час для заявок/журнала событий, RTO 4 часа для основных сервисов; подтвердить тестом восстановления. Банковские операции и проводки требуют отдельного подтверждаемого журнала и сверки; нельзя считать часовую потерю финансов допустимой по умолчанию.
- Копировать код и manifests версий, data, загруженные документы, реестры, queue/inbox/outbox, бюджетный журнал, Excel и нужные настройки. Для SQLite использовать online backup/согласованный snapshot, для файловых реестров — копию под общей блокировкой; не копировать произвольно меняющиеся файлы.
- Шифрованная копия на независимом хранилище; резервные ключи отдельно. Стартовое хранение: 7 ежедневных, 4 еженедельных, 3 месячных копии с корректировкой под обязательные сроки данных. Проверка хешей каждого набора, регулярное восстановление в изоляции без отправки сообщений и платежей. Работающий сервис не имеет права удалить все независимые копии.

## Безопасное обновление

Сначала сопоставить действующий сервер с репозиторием, включая отсутствующие файлы. Не накатывать весь config.php из публичного патча поверх production. Секреты и данные не попадают в сборку; существующие API остаются совместимыми.

Порядок: локальная правка → проверки Python/PHP и критических сценариев → изолированный стенд с обезличенными данными и тестовым банком/MAX → резервная копия и проверка восстановления → конкретный reviewed diff и план отката → согласованная публикация → smoke tests и наблюдение. В этом аудите публикация не выполняется.

Обновления включаются feature flags по компонентам и небольшой группе пользователей. Миграции сначала расширяют схему, затем переключают чтение/запись; удаление старых полей — отдельным этапом. Перед сменой единственного писателя остановить получение новых команд на короткое контролируемое время и сохранить очередь. Не запускать старый и новый consumer одного MAX-бота одновременно.

Код откатывается на предыдущую версию с совместимой схемой. Откат не повторяет письма, выплаты и банковские запросы; внешние эффекты сверяются и компенсируются отдельной операцией. При аварийной остановке ИИ сохраняются сайт, ручная диспетчеризация и источник событий.
